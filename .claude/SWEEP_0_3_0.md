Generated by .claude/sweep_0_3_0.py on a 12-core machine.
Build is `phobic.build(...)` with default load_factor=0.5;

### Comparison points

vs phobic 0.2.0 (from `.claude/SESSION_NOTES.md`, 8 cores):
- 1M parallel: 2.0 s in 0.2.0; **0.34 s in 0.3.0** (5.9x faster), bpk 1.18 to 1.17 (slightly better).

vs maph's reference `partitioned_phf<phobic4>` (from maph's BENCHMARK_RESULTS.md):
- 10M build: 7.4 s in maph; **3.72 s in 0.3.0** (2.0x faster), bpk 2.76 to 1.16 (2.4x more space-efficient).

vs maph's `shock_hash128` (the space champion in maph):
- 10M bpk: 1.54 in 14.3 s with range/keys=1.85; phobic 0.3.0 hits 1.16 in 3.72 s and is minimal. Phobic wins on every axis at this N.

## Auto num_shards heuristic

`num_shards` is now a pure function of N (independent of `num_threads`),
so `phobic.build(keys, seed=42)` produces byte-identical output regardless
of CPU count. Below 32K keys: 1 shard. Above: `(N + 15999) / 16000`.

## Notes on the speedup ceiling

Parallel build speedup is ~2x even at 12 threads. Profiling suggests the
remainder is dominated by:

- Single-threaded key encoding under the GIL (~500 ms at 10M)
- malloc/free across many small per-shard buffers (allocator contention)
- shard distribution pass (single-threaded scan)

All three are 0.4.0 candidates: per-shard arena allocators, parallel
shard distribution, optional numpy bytes-array input to skip Python-side
encoding. None are needed to land 0.3.0.

## Batch query summary

| N | sample size | 1 thread (ns/key) | 8 threads (ns/key) |
|---:|---:|---:|---:|
| 1K | 1K | 142 | 141 |
| 100K | 10K | 149 | 166 |
| 1M | 50K | 175 | 151 |
| 10M | 50K | 211 | 174 |

Batch parallelism is small (~1.2x at most) because the work per key
(~150 ns of C: one wymix, one bucket lookup, one slot mod) is small
relative to per-key Python overhead (PyBytes encoding under GIL,
PyLong_FromSize_t per output). A numpy bulk-input + bulk-output path
would shift this dramatically (4-5x feasible) but is a 0.4.0 feature.
